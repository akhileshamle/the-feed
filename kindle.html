DSA Micro-Session: Monotonic Stack and the Next Greater Element

Cheatsheet item: Monotonic stack, an O(n) pattern for "next greater/smaller" questions.

1. Recall (3 min, no peeking)

Close your editor and answer from memory:

  • What does the stack hold: values or indices? Why?
  • Does the stack stay increasing or decreasing from bottom to top when you look for the next greater element?
  • What is the time complexity, and why isn't it O(n²) even though there's a loop inside a loop?

2. Problem (5 min)

Given temps = [73, 74, 75, 71, 69, 72, 76, 73], return an array where result[i] is how many days you wait until a warmer temperature. Use 0 if no warmer day comes.

Write it in Swift:

func dailyTemperatures(_ temps: [Int]) -> [Int] {
    // your code
}

Before checking, trace your solution by hand on the input above.

3. Stretch (2 min)

How would you change it to find the previous smaller element? What happens with a circular array, as in "Next Greater Element II"?

---

Answer:

Recall:

  • The stack stores indices. An index gives you the value (temps[i]) and the distance (i - j).
  • For next greater, the stack is decreasing from bottom to top. Each new value pops every smaller value below it.
  • It runs in O(n) time and O(n) space. Each index is pushed once and popped at most once.

Solution:

func dailyTemperatures(_ temps: [Int]) -> [Int] {
    var result = Array(repeating: 0, count: temps.count)
    var stack: [Int] = []
    for (i, t) in temps.enumerated() {
        while let last = stack.last, temps[last] < t {
            stack.removeLast()
            result[last] = i - last
        }
        stack.append(i)
    }
    return result
}

Output: [1, 1, 4, 2, 1, 1, 0, 0]

Stretch:

  • Previous smaller: pop while temps[top] >= t. After popping, the top of the stack is the answer for i.
  • Circular array: loop i from 0 to 2n - 1 and read nums[i % n]. Push indices only during the first pass (i < n).

Thursday Math: Will a Rare Crash Ever Reach This User?

Tool of the day: #4 — P(at least one) = 1 − (1 − p)^n

A low chance per try still adds up over many tries. To find the odds that something happens at least once, work out the odds that it never happens and subtract that from 1.

Shortcut: when p is small, (1 − p)^n ≈ e^(−np). So P(at least one) ≈ 1 − e^(−np)

Useful values of e^(−x):

  • x = 0.5 → 0.61
  • x = 0.7 → 0.50
  • x = 1 → 0.37
  • x = 2 → 0.14
  • x = 3 → 0.05

Today's problem

Your app crashes in 0.2% of sessions. Crashlytics calls that "99.8% crash-free," and the dashboard is green.

A typical engaged user opens the app 10 times a day.

  1. What's the chance this user hits at least one crash in a month (30 days)?
  2. After about how many sessions does the user reach 50/50 odds of having seen a crash?
  3. Bonus: you cut the crash rate in half, to 0.1%. What's the new monthly chance from part 1?

Do it in your head with the e^(−x) table above. No calculator.

Why it matters: "Crash-free sessions" and "crash-free users" can tell very different stories. Your heaviest users, often the ones who write reviews, live in the second number.

---

Answer:

  1. n = 300 sessions and p = 0.002, so np = 0.6. That gives 1 − e^(−0.6) ≈ 1 − 0.55 ≈ 45%. Close to a coin flip, even with a 99.8% crash-free rate.
  2. You need e^(−np) = 0.5, so np ≈ 0.69 and n ≈ 0.69 / 0.002 ≈ 347 sessions, or about 35 days. (This is the same 0.69 behind the Rule of 72.)
  3. np = 0.3, so 1 − e^(−0.3) ≈ 1 − 0.74 ≈ 26%. Halving the crash rate takes the monthly chance from about 45% to about 26%, a drop of roughly 40% rather than half. The curve flattens as np grows, so for heavy users the improvement looks smaller than the rate change suggests.

Physics Micro-Session: Feedback Loops (dx/dt = kx)

Concept (1 min) When the rate at which something changes depends on how much of it there already is, you have a feedback loop. The equation dx/dt = kx gives x(t) = x₀·e^(kt).

  • k > 0 (positive feedback): growth compounds. It is slow at first, then sudden.
  • k < 0 (negative feedback): the system corrects itself and settles. Think of a thermostat.

A quick shortcut is the Rule of 70. Doubling (or halving) time ≈ 70 / (percent rate per period).

Lens (1 min) The real question is "what does this feed back into?", not "how big is it now?" A small k that runs for a long time beats a big push that happens once.

iOS example (2 min)

  • Positive loop (bad): messy module → slow builds → rushed fixes → messier module. Tech debt compounds like interest.
  • Positive loop (good): better tests → safer refactors → cleaner code → tests that are easier to write.
  • Negative loop (stabilizer): a CI check that fails the build when app launch time goes past a set budget. Every time drift happens, it gets pushed back.

To change a system, find the sign of k. Slowing down a bad loop usually means adding a negative-feedback check, like a lint rule, a size budget or a weekly review. Extra effort alone doesn't do it.

Drill (1 min) Your project's clean build time grows about 5% per month as features are added. It's 4 minutes today.

  1. Roughly how long until it's 8 minutes?
  2. About how long would it be after 2 years if nothing changes?
  3. Name one negative-feedback mechanism that would set k ≤ 0.

Apply today: Pick one habit or metric in your week. Is its k positive or negative? Write down one change that would flip or reduce it.

---

Answer:

  1. 70 / 5 ≈ 14 months to double, so about 8 minutes.
  2. 24 months ≈ 1.7 doublings → 4 × 2^1.7 ≈ 13 minutes (e^(0.05×24) ≈ 3.3×).
  3. Examples: a CI build-time budget that fails when exceeded, a recurring "modularize one target" ticket, or required build caching and binary frameworks for stable modules.
