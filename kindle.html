Signal vs Noise: Don't Trust One Launch

Concept: One measurement mixes signal with noise. Averaging N independent samples shrinks the noise:

σ_mean = σ / √N

The catch is the square root. Cutting noise in half takes 4× the samples. Cutting it to a tenth takes 100×.

Why it matters: People react to single data points all the time. One slow standup, one bad sprint, one angry App Store review. Before you judge, ask how big the noise is compared with the change you think you see.

iOS lens: You run your app once on a device and cold launch takes 480 ms. Yesterday it took 420 ms. Is that a regression? Thermal state, background daemons, disk cache and other processes on the device can easily move a single launch by ±100 ms. With one run each, you can't tell a regression from a random dip.

The fix is to measure many runs and compare averages. XCTest's measure(metrics:) with XCTApplicationLaunchMetric and several iterations does this, and so does looking at MetricKit percentiles across many users instead of a single report.

Rule of thumb: You can call an effect real when it's at least 2× σ_mean. You need about 3× before you'd block a release over it.

Today's question: Cold launch time on your test device has a run-to-run standard deviation of σ = 120 ms. You want to reliably detect a 30 ms regression, which means getting σ_mean down to about 15 ms. Roughly how many launches per build do you need to average?

Real-life drill: Pick one metric you reacted to this week, such as a crash count, a build time or a review score. Estimate its noise and decide whether that change was actually a signal.

Answer

σ_mean = σ/√N, so √N = 120/15 = 8, which gives N ≈ 64 launches per build. Ten runs would only get σ_mean to about 38 ms, which is bigger than the 30 ms regression you're looking for. To halve the noise again (7.5 ms), you'd need about 256 runs.

DSA Micro-Session: Union-Find (Disjoint Set Union)

Today's item: Union-Find with path compression and union by rank.

Recall first (about 4 minutes, no peeking)

Try to answer these from memory, out loud or on paper:

  1. What two operations does Union-Find support, and what does each return or do?
  2. What is path compression, and which operation uses it?
  3. What is union by rank (or by size), and what problem does it prevent?
  4. With both optimizations, what is the amortized time per operation?
  5. Name two classic problems where Union-Find is the right tool.
  6. How do you detect a cycle in an undirected graph with it?

Code it (about 4 minutes)

Write a minimal Swift UnionFind struct with find(_:) and union(_:_:) -> Bool. union should return false if the two nodes were already connected.

Self-check (about 2 minutes)

Run your code against [(0,1), (1,2), (2,0)]. Which call to union returns false, and what does that tell you?

---

Answer

  1. find(x) returns the root (representative) of x's set. union(a, b) merges the two sets that contain a and b.
  2. During find, every node on the path gets pointed straight at the root, so later lookups are faster.
  3. You attach the shorter tree under the taller one. Without this, the trees can turn into long chains with O(n) depth.
  4. O(α(n)), the inverse Ackermann function. In practice that is constant time.
  5. Kruskal's MST, number of connected components / provinces, redundant connection, accounts merge, and checking whether a graph is a valid tree.
  6. For each edge (u, v), if find(u) == find(v) there is a cycle. Otherwise call union(u, v).
struct UnionFind {
    private var parent: [Int], rank: [Int]
    init(_ n: Int) { parent = Array(0..<n); rank = Array(repeating: 0, count: n) }

    mutating func find(_ x: Int) -> Int {
        if parent[x] != x { parent[x] = find(parent[x]) }
        return parent[x]
    }

    mutating func union(_ a: Int, _ b: Int) -> Bool {
        let (ra, rb) = (find(a), find(b))
        guard ra != rb else { return false }
        if rank[ra] < rank[rb] { parent[ra] = rb }
        else if rank[ra] > rank[rb] { parent[rb] = ra }
        else { parent[rb] = ra; rank[ra] += 1 }
        return true
    }
}

Self-check: union(2, 0) returns false. Nodes 0 and 2 were already connected through 1, so the edge (2,0) closes a cycle.

Friday Math: The Crash-Free Illusion

Today's tool: #4, P(at least one) = 1 − (1 − p)^n

A small per-try risk adds up over many tries. Your crash dashboard shows it per session, but users notice it over a whole month.

Problem

Your app has a 99.8% crash-free session rate, so each session has p = 0.002 chance of crashing. A typical user opens the app 3 times a day for 30 days.

  1. What is the chance that a typical user sees at least one crash this month?
  2. Product wants no more than 5% of users to see a crash in a month. What crash-free session rate do you need?

Method

  • Count the tries: n = 3 × 30 = 90 sessions.
  • Work out the chance of no crash at all: (1 − p)^n.
  • Subtract that from 1.
  • Shortcut: when n·p is small, the answer is close to n·p, just a little under it. That's a fast check you can do in your head.
  • For part 2, run the formula backwards. Set the answer to 0.05 and solve for p. The shortcut gives p ≈ 0.05 / n.

Why it matters

A per-event metric can look excellent while users have a poor time. "99.8%" sounds great, but users count months, not sessions. Use the same check for flaky tests in CI: a test that fails 1% of the time, across 50 test runs a day, fails at least once on about 40% of days.

Try it before you scroll: get a rough estimate with the shortcut, then the exact value.

Answer

  1. n·p = 90 × 0.002 = 0.18, so the shortcut says about 18%. Exact: 1 − 0.998^90 ≈ 1 − e^(−0.180) ≈ 1 − 0.835 = about 16.5%, roughly 1 user in 6 sees a crash each month.
  2. Solve 1 − (1 − p)^90 = 0.05. The shortcut gives p ≈ 0.05 / 90 ≈ 0.056%. Exact: p = 1 − 0.95^(1/90) ≈ 0.057%, which means a crash-free session rate of about 99.94%. That is about 3.5× fewer crashes per session than today.
