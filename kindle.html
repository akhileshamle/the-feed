Friday: Fermi estimation

Break a number you can't look up into 3–5 factors you can guess, then multiply them. Each guess may be off, but the errors tend to cancel, so the result usually lands within a factor of 2–3 of the truth.

Problem: Your iOS team has 8 engineers. Each pushes branches that trigger a CI build of about 12 minutes. Roughly how many engineer-hours per year does the team spend waiting on CI builds, unable to do focused work?

Try it first:

  • Guess how many builds one engineer triggers on a typical workday.
  • Not every minute of a build is lost. Guess what fraction of build time someone is actually blocked.
  • Use about 230 working days in a year.

Why it matters: A rough number like this lets you argue for a faster CI machine or build caching in money terms, without waiting for a dashboard.

Answer

One reasonable estimate (your guesses can differ):

  • Builds per engineer per day: 6
  • Team builds per day: 8 × 6 = 48
  • Build minutes per day: 48 × 12 = 576 min ≈ 9.6 h
  • Fraction of that time someone is blocked: 1/3, so 9.6 / 3 ≈ 3.2 h/day
  • Per year: 3.2 × 230 ≈ 736 h ≈ 740 engineer-hours

That is about 18 full 40-hour work weeks a year. At about $100 per engineer-hour, it costs around $74k a year. Halving build time would save about $37k a year, which is more than a fast CI Mac costs.

Friday: Feedback Loops, dx/dt = kx

The idea: A feedback loop is any system where the output feeds back into its own rate of change. If k > 0, growth makes more growth (compounding). If k < 0, the system pulls itself back toward a set point (stabilizing).

Question for today: Your iOS project has 20 flaky UI tests. Because people re-run failed builds and don't fix them, the count grows about 5% per week. How many flaky tests will there be in 12 weeks? Roughly how long until the count doubles?

Real-life application (software engineering): retry storms

  • When the backend slows down, every app instance retries right away. The extra load slows the server further, which causes more retries. That is k > 0.
  • Exponential backoff with jitter plus a circuit breaker turns this into k < 0: the more failures there are, the fewer requests clients send, so the server can recover.
  • Check your URLSession retry logic today. Ask whether a failure makes the next request more likely or less likely.

2-minute exercise:

  1. Write down one loop in your current week, such as code review backlog, sleep and focus, or tech debt.
  2. Mark its sign: + (compounds) or − (stabilizes).
  3. Name one lever that would flip a harmful + into a −, or strengthen a helpful +.

Log it: date, concept, my answer, what I applied.

Answer

N(12) = 20 × 1.05¹² ≈ 20 × 1.80 ≈ 36 flaky tests. Doubling time ≈ 70 / 5 = about 14 weeks (rule of 70). To flip the sign to k < 0, make a flaky failure cost something. For example, auto-quarantine the test and open a ticket instead of allowing a silent re-run. Then each failure leads to a fix, and the count goes down.

Signal vs Noise: Don't Trust One Launch

Concept: One measurement mixes signal with noise. Averaging N independent samples shrinks the noise:

σ_mean = σ / √N

The catch is the square root. Cutting noise in half takes 4× the samples. Cutting it to a tenth takes 100×.

Why it matters: People react to single data points all the time. One slow standup, one bad sprint, one angry App Store review. Before you judge, ask how big the noise is compared with the change you think you see.

iOS lens: You run your app once on a device and cold launch takes 480 ms. Yesterday it took 420 ms. Is that a regression? Thermal state, background daemons, disk cache and other processes on the device can easily move a single launch by ±100 ms. With one run each, you can't tell a regression from a random dip.

The fix is to measure many runs and compare averages. XCTest's measure(metrics:) with XCTApplicationLaunchMetric and several iterations does this, and so does looking at MetricKit percentiles across many users instead of a single report.

Rule of thumb: You can call an effect real when it's at least 2× σ_mean. You need about 3× before you'd block a release over it.

Today's question: Cold launch time on your test device has a run-to-run standard deviation of σ = 120 ms. You want to reliably detect a 30 ms regression, which means getting σ_mean down to about 15 ms. Roughly how many launches per build do you need to average?

Real-life drill: Pick one metric you reacted to this week, such as a crash count, a build time or a review score. Estimate its noise and decide whether that change was actually a signal.

Answer

σ_mean = σ/√N, so √N = 120/15 = 8, which gives N ≈ 64 launches per build. Ten runs would only get σ_mean to about 38 ms, which is bigger than the 30 ms regression you're looking for. To halve the noise again (7.5 ms), you'd need about 256 runs.
