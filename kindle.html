DSA Micro-Session: Binary Search on a Rotated Sorted Array

Time: 10 minutes. Recall first, then check.

1. Recall (3 min)

Cover the solution. Write the algorithm from memory in Swift or pseudocode.

Problem: [4, 5, 6, 7, 0, 1, 2] is a sorted array rotated at an unknown pivot, with distinct values. Find the index of target in O(log n).

Before you code, answer these:

  • At any mid, which half is guaranteed sorted?
  • How do you decide whether target lies in that sorted half?
  • What are the loop condition and the pointer updates?

2. Attempt (4 min)

Code search(_ nums: [Int], _ target: Int) -> Int. It returns -1 if the target isn't found. Then trace target = 0 on the array above.

3. Check (3 min)

Compare your answer with the Answer section below.

Stretch: What breaks if duplicates are allowed? What is the worst-case time?

Answer:

func search(_ nums: [Int], _ target: Int) -> Int {
    var lo = 0, hi = nums.count - 1
    while lo <= hi {
        let mid = lo + (hi - lo) / 2
        if nums[mid] == target { return mid }
        if nums[lo] <= nums[mid] {            // left half sorted
            if nums[lo] <= target && target < nums[mid] {
                hi = mid - 1
            } else {
                lo = mid + 1
            }
        } else {                              // right half sorted
            if nums[mid] < target && target <= nums[hi] {
                lo = mid + 1
            } else {
                hi = mid - 1
            }
        }
    }
    return -1
}

Trace, target = 0:

  • lo=0, hi=6, mid=3 (7). Left half [4..7] is sorted and 0 isn't in it, so lo=4.
  • lo=4, hi=6, mid=5 (1). Left half [0,1] is sorted and 0 is in it, so hi=4.
  • lo=4, hi=4, mid=4 (0). Found, so return 4.

Key idea: one half around mid is always sorted. Check whether the target falls in that half, and discard the other half. The <= in nums[lo] <= nums[mid] matters when lo == mid.

Stretch answer: with duplicates, nums[lo] == nums[mid] == nums[hi] makes the sorted half ambiguous. You can only shrink with lo += 1; hi -= 1. The worst case degrades to O(n).

Physics Drill: Feedback Loops (dx/dt = kx)

Concept: The rate of change of x is proportional to x itself. If k > 0, growth feeds on itself and compounds. If k < 0, deviations shrink and the system settles. Solution: x(t) = x₀·e^(kt).

Question: In a feedback loop, what decides whether things explode or stabilize?

The sign of k decides it, and the magnitude of k sets the speed. The doubling time for k > 0 is ln2 / k ≈ 0.7 / k. The decay time constant for k < 0 is 1 / |k|.

Rule of thumb: If something grows about r% per period, it doubles in roughly 70 / r periods.

Apply it to an iOS engineer's life:

  1. Tech debt (k > 0): Messy code makes changes slower. Slower changes mean more shortcuts, and shortcuts mean messier code. The loop compounds, so the fix is to break it early with small refactors.
  2. Test coverage (k < 0 on bugs): Tests catch regressions, which gives fewer bugs, which means less firefighting. That frees time to write more tests. This is a stabilizing loop that can also turn into a virtuous growth loop.
  3. Learning: Each concept you learn makes the next one easier to attach. If you gain 1% per day, the factor is 1.01^365 ≈ 37×. The caveat is that real growth saturates (logistic, not pure exponential), so check whether you are still on the steep part of the curve.

Today's drill (one real-life item): Pick one habit or system you have, such as the app's crash rate, your PR review backlog, or your sleep. Write down:

  • What feeds back into what?
  • Is k positive or negative right now?
  • What one small change would flip the sign or shrink |k|?

Quick check: A backlog grows 5% per week with no intervention. About how many weeks until it doubles?

Answer: About 14 weeks (70 / 5 = 14; exactly ln2 / ln1.05 ≈ 14.2).

Physics Drill: Feedback Loops

Concept: dx/dt = kx. The rate of change is proportional to the current amount.

  • k > 0 is a reinforcing loop. It compounds, like interest, viral growth or tech debt.
  • k < 0 is a stabilizing loop. It decays toward a set point, like a thermostat, a retry backoff or a code review gate.

Solution: x(t) = x₀·e^(kt). The doubling time is ln(2)/k ≈ 0.69/k.

Question to ask: What is x, and what sets the sign of k?

Engineer's lens: Untested code makes the next change riskier. Risk makes people ship less often, so changes batch up and get riskier still. That is a positive loop. CI, small PRs and feature flags add a negative loop that pulls x back down.

Real-life application (2 min):

  1. Pick one item, such as your inbox, your workout habit or your app's crash backlog.
  2. Name x, the quantity that changes.
  3. Ask whether more x makes more x (k > 0) or less x (k < 0).
  4. Find one cheap action that flips k from positive to negative.

Drill problem: Your untriaged bug backlog grows about 7% per week because each unfixed bug causes follow-on bugs. You have 40 bugs now, and you do nothing.

  1. What is the doubling time?
  2. Roughly how many bugs will there be after 20 weeks?

Use ln(2) ≈ 0.69 and e^1.4 ≈ 4.

Answer: The doubling time is 0.69 / 0.07 ≈ 10 weeks. After 20 weeks the backlog doubles twice, so it is about 40 × 4 = 160 bugs. (The exact compounding gives 40 × 1.07²⁰ ≈ 155, so the estimate is close.) Fixing even a fraction of the bugs each week makes k negative, and the backlog then shrinks instead of growing.
