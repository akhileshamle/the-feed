Friday: Debugging and Production

Why it matters: A launch watchdog kill gets no crash handler and leaves no breadcrumb in most crash SDKs, so it can sit unnoticed while it drains retention. At scale, a 1% launch failure rate on older devices means hundreds of thousands of users who see an app that "just closes".

Scenario: Version 4.8 is at day 3 of a phased release. Xcode Organizer shows 0x8badf00d launch terminations up 5x. They are almost all on A12/A13 devices, and the rate is still climbing. The diff has two suspects: a heavyweight Core Data migration and a new analytics SDK that starts in didFinishLaunching behind a remote flag. The flag value is read from cache at launch and refreshed after the first screen appears. A hotfix needs at least 48 hours, even with expedited review.

Recall first

  1. Why can't the kill switch help the users who are hurt most?
  2. How do you get the main-thread stack when you can't reproduce the kill locally?
  3. What would you do in the next hour, and why?

Answer

Decision: Pause the phased release now and flip the flag off anyway, since that helps users who haven't failed yet. Then pull the main-thread stacks from the watchdog reports in Organizer and from MXAppLaunchDiagnostic in MetricKit. If the stacks show a synchronous migration on the main thread, that is a crash loop: the watchdog kills the app mid-migration, so it restarts on every launch. Ship a hotfix that renders UI first and migrates in the background.

container.persistentStoreDescriptions.first?.shouldAddStoreAsynchronously = true
showMigratingPlaceholder()
container.loadPersistentStores { _, error in /* swap in real UI */ }

Rejected:

  • Rolling back: the App Store has no binary rollback.
  • Flag only: users killed during launch never reach the flag refresh.
  • Local repro first: the debugger turns off the watchdog, and fast devices hide the problem.

Main risk: Partially migrated stores. The hotfix must cope with a store that was interrupted mid-migration.

Common mistake: Measuring launch with Xcode attached, or on a current device, and declaring it fixed.

Friday: Trees (DFS, BFS, recursion)

When to reach for this pattern: Use it when the data is hierarchical and each node's answer depends on its children, its parent, or its depth.

Problem: Deepest Leaves Sum You are given the root of a binary tree. Return the sum of the values of all nodes on the deepest level.

Example:

        1
       / \
      2   3
     / \   \
    4   5   6
   /         \
  7           8

The deepest level is level 4, which holds nodes 7 and 8. Output: 15.

Recall first

  1. What is the brute force? (Hint: two passes.)
  2. What is the key observation that lets one pass do the job?
  3. What time and space should you aim for, and what does space depend on?

Answer

Approach. The brute force takes two passes: one DFS to find the maximum depth, then a second DFS that adds up the nodes at that depth. The key observation is that a level-order BFS handles the tree one full level at a time. Keep a running sum for the current level and reset it at the start of each level. When the queue empties, the last level's sum is the answer. A one-pass DFS also works: carry the depth down, and whenever you reach a depth greater than the best so far, reset the sum.

if root is null: return 0
queue = [root]
while queue not empty:
    level_sum = 0
    repeat len(queue) times:
        node = queue.pop_front()
        level_sum += node.val
        if node.left:  queue.push(node.left)
        if node.right: queue.push(node.right)
return level_sum

Complexity. Time is O(n), since each node is visited once. Space is O(w) for BFS, where w is the maximum width of the tree (up to n/2 for a complete tree). The DFS version uses O(h) for the recursion stack, where h is the height.

Friday: Fermi Estimation

Break a number you can't know into 3–5 factors you can roughly guess, then multiply them. Round each factor to an easy number. The errors tend to cancel out, so you usually land within a factor of 2–3 of the true value.

Problem

Your team's API serves about 50 requests per second, all day, every day. Each request writes about 4 log lines of about 250 bytes each. Logs are kept for 30 days, and storage costs about $0.10 per GB per month.

Roughly how much does storing these logs cost each month? Then a manager proposes logging 20 lines per request "for better debugging." What would the bill become?

Try it first

  • Round seconds in a day to a power of ten.
  • Get bytes per day first, then the total held at any moment under 30-day retention.
  • The second question doesn't need a fresh calculation from scratch.

Why it matters: Fermi estimates let you size a cloud bill, a market or a hiring plan in two minutes. They also show you which factor is worth checking before anyone signs off.

Answer

  • Seconds per day: 86,400 ≈ 10⁵
  • Requests per day: 50 × 10⁵ = 5 × 10⁶
  • Bytes per request: 4 × 250 = 1,000 B ≈ 1 KB
  • Data per day: 5 × 10⁶ × 1 KB = 5 × 10⁹ B ≈ 5 GB/day
  • Held at any time (30-day retention): 5 × 30 = 150 GB
  • Monthly cost: 150 × $0.10 ≈ $15/month

With exact figures (86,400 s gives 4.32 GB/day and about 130 GB stored), the bill is about $13, close to the estimate.

With 20 lines per request, every byte count is 5× larger: about 750 GB stored, so about $75/month. Storage alone is still cheap. Search and indexing tools usually charge per GB ingested, which is a 5× jump from 5 to 25 GB/day, so that's the factor to check first.
